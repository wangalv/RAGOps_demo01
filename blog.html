From RAG PoC to Production: What the Demo Doesn't Tell You

A practical study of RAG retrieval quality, Recall, Precision and the engineering gap between a successful demo and a reliable production system.

The RAG Demo Looks Easy

You've probably seen the demo.

Upload a set of documents.

Ask a question.

The system finds the relevant information and an LLM produces a clear, natural-language answer.

It works.

And that naturally leads to the next question:

"If the PoC works, how difficult can it be to put it into production?"

This is where the story gets interesting.

A RAG PoC can be surprisingly easy to build.

A production RAG system is a very different animal.

The difference is not simply infrastructure, scalability or API management.

The harder question is:

Can we trust the system to find the right information consistently — including the questions we didn't think of when we built the PoC?

That question led me to this study.

I built and evaluated a RAG pipeline against the NSW Health Services Act 1997, running 15 retrieval experiments across several different approaches.

What I found was simple:

A successful RAG demo proves that RAG can work. It does not prove that RAG will work reliably in production.

First, What Is RAG?

Before looking at the experiments, it is worth understanding what actually happens inside a RAG system.

RAG stands for Retrieval-Augmented Generation.

The basic idea is straightforward:

User Question
      ↓
Retrieve relevant document chunks
      ↓
Put those chunks into the LLM context
      ↓
LLM generates the answer

Instead of asking the LLM to rely entirely on what it learned during training, we give it relevant information from an external knowledge source.

For example, imagine a user asks:

"What penalty applies if someone breaches Section X?"

A RAG system might:

  1. Convert the question into a representation that can be searched.
  2. Search the document collection.
  3. Retrieve the most relevant passages.
  4. Give those passages to the LLM.
  5. Ask the LLM to answer using the retrieved evidence.

The important point is that the LLM is only as good as the context it receives.

And this is where the first production problem appears.

Retrieval Comes Before Generation

When people talk about RAG accuracy, the conversation often jumps straight to the LLM.

But there are actually two very different questions:

Question 1 — Did we find the right information?

This is the retrieval problem.

Question 2 — Did the LLM use that information correctly?

This is the generation problem.

These are different failure modes.

Consider this example.

The correct answer exists in the knowledge base.

But the retriever fails to return the relevant passage.

The LLM never sees it.

No amount of prompt engineering can make the model answer from information that was never provided to it.

This is why retrieval quality deserves to be measured independently.

Recall: Did We Find the Answer?

One of the most important retrieval metrics is Recall@K.

Suppose the system retrieves the top 5 chunks.

Recall@5 asks:

Did the correct information appear somewhere in those five chunks?

For example:

100 questions
80 questions → correct passage found in top 5
20 questions → correct passage not found

Then:

Recall@5 = 80%

This does not mean that the final answers are 80% correct.

It means something more specific:

For 80% of the questions, the retrieval system gave the LLM a chance to find the answer.

That distinction is extremely important.

If Recall@5 is only 70%, then for roughly 30% of the questions, the correct evidence never reached the LLM.

The model cannot reliably answer information it never received.

Precision: How Much Noise Did We Retrieve?

Recall tells us whether we found the answer.

Precision asks a different question:

Of the information we retrieved, how much of it was actually relevant?

Imagine we retrieve 5 chunks:

Chunk 1 → Relevant
Chunk 2 → Irrelevant
Chunk 3 → Irrelevant
Chunk 4 → Relevant
Chunk 5 → Irrelevant

Only 2 of the 5 chunks are relevant.

So:

Precision@5 = 40%

We found the answer.

But we also gave the LLM a lot of noise.

This matters because irrelevant context consumes tokens, increases cost, can distract the model, and can make the final answer less reliable.

So there is an important trade-off:

High Recall means we are less likely to miss the answer.
High Precision means we are less likely to bury the answer in noise.

A production RAG system needs to care about both.

Then What Is Top-K?

This brings us to another deceptively simple parameter:

K.

If K = 5, the retriever returns the top 5 results.

If K = 10, it returns the top 10.

Increasing K usually gives the system a bigger net.

That can improve Recall.

But it also introduces more information — including potentially irrelevant information.

For example:

Top-K = 3

[Relevant]
[Relevant]
[Irrelevant]

versus:

Top-K = 10

[Relevant]
[Relevant]
[Irrelevant]
[Irrelevant]
[Irrelevant]
[Relevant]
[Irrelevant]
[Irrelevant]
[Irrelevant]
[Irrelevant]

The second system may have better recall.

But it may also have worse precision.

And now we have a fundamental RAG engineering problem:

How many documents should we retrieve?

There is no universal answer.

It depends on the documents, the questions, the chunking strategy, the retrieval model, the context window and the downstream generation model.

This is one reason why "the RAG works" is not really an evaluation strategy.

Phase 1 — The PoC Looks Great

This was the first stage of my study.

I created a small manually designed Golden Set of 21 questions against the NSW Health Services Act.

The initial results looked very good.

Recall@3 = 0.881

In other words, the correct passage appeared in the top three results for approximately 88% of the questions.

If this were a typical PoC presentation, this is probably where the conversation would become very positive.

The demo works.

The answers look good.

The retrieval score looks good.

So why not move to production?

Because the benchmark itself was part of the problem.

Phase 2 — Ask Harder Questions

The 21 questions were created by someone who already understood the Act.

They were clean.

They were predictable.

They reflected the structure of the source material.

Real users are different.

Users don't necessarily ask:

"What does Section 42 say?"

They may ask:

"What happens if someone does this?"
"Is there a penalty for doing X?"
"What happens if this requirement isn't followed?"
"Does this apply when the person is operating under condition Y?"

The wording of the question may have very little overlap with the wording of the legislation.

So I expanded the benchmark to 79 questions, covering a broader range of realistic query patterns.

The result changed dramatically.

The baseline became:

Recall@5 = 0.750

And Precision@5 was approximately:

0.169

The PoC's 88% retrieval result had become a much less comfortable production baseline.

This was the first major lesson:

Your benchmark can make your RAG system look better than it really is.

A benchmark is not just a measurement tool.

It defines what "good" means.

Phase 3 — Now We Start Engineering

Once the harder benchmark exposed the weaknesses, the next question became:

Can we improve retrieval?

I tested several approaches.

1. Better Chunking

Instead of treating large sections of legislation as single chunks, I experimented with more granular subsection-level chunks.

The idea is simple:

Give the retriever smaller, more precise targets.

2. Parent-Child Retrieval

Instead of searching only large passages, retrieval can happen at a smaller level while returning a larger parent context.

This tries to balance retrieval precision with context completeness.

3. Query Routing

Different questions have different structures.

A question about a penalty is not necessarily the same type of question as a question about a prohibition or a cross-reference.

I experimented with using an LLM to classify the query and route it through different retrieval strategies.

4. HyDE

HyDE — Hypothetical Document Embeddings — takes another approach.

Instead of searching directly using the user's question, an LLM generates a hypothetical answer or document-like representation and uses that for retrieval.

The motivation is to reduce the vocabulary gap between:

How the user asks the question

and:

How the legislation is actually written

The Surprising Result

After combining these structural techniques, the Recall@5 result became:

0.753

The original baseline was:

0.750

So after all that engineering:

+0.003

Three tenths of a percentage point.

This was one of the most interesting findings in the study.

Some techniques sound sophisticated.

Some techniques are genuinely useful.

But sophisticated architecture does not automatically translate into meaningful retrieval improvement.

And this is exactly the kind of thing a PoC does not tell you.

Phase 4 — Reranking Changes the Picture

The more significant improvement came from a different idea:

Reranking.

Instead of relying entirely on embedding similarity to determine the final order of results, I retrieved a candidate set and then used an LLM to evaluate the relevance of those passages.

The reranker evaluated each retrieved passage against a set of legal-aware rules and assigned a relevance score.

The results were then reordered and the best passages retained.

The result:

Recall@5 = 0.802

Compared with the Phase 3 result of 0.753, this was a 5.2 percentage point improvement.

But there was a trade-off.

The reranking approach required additional LLM calls for every query.

So the engineering question changed again:

Is the additional accuracy worth the additional latency and cost?

That is a production question.

A PoC often doesn't ask it.

What the PoC Didn't Show Me

After going through these experiments, I started to see RAG differently.

A RAG system is not simply:

Documents → Vector Database → LLM

A production system has multiple quality surfaces.

1. Retrieval

Did we find the right information?

Metrics include:

  • Recall@K
  • Precision@K
  • MRR
  • nDCG
  • retrieval latency

2. Generation

Did the LLM actually use the retrieved information correctly?

Now we care about:

  • Faithfulness
  • Answer relevance
  • Citation accuracy
  • Hallucination
  • Context utilisation

3. Operations

And then there is everything around the model:

  • What happens when documents change?
  • What happens when legislation is amended?
  • What happens when users ask new types of questions?
  • How do we detect a regression?
  • How do we know whether a new embedding model is actually better?
  • How do we evaluate a new chunking strategy?
  • How much does every query cost?
  • How do we monitor quality after deployment?

This is where RAGOps starts to matter.

Production RAG Is a Moving Target

Imagine your RAG system goes live today.

Six months later:

  • A document changes.
  • A new regulation is introduced.
  • Users start asking different questions.
  • You change the embedding model.
  • You change the chunking strategy.
  • You add query expansion.
  • You introduce reranking.
  • You change the LLM.

The system is no longer the same system you originally tested.

And yet, without a repeatable evaluation process, you may still be reporting the original PoC accuracy number.

That number is now almost meaningless.

This is why RAG evaluation cannot be a one-off activity.

It needs to become part of the engineering lifecycle.

From RAG Evaluation to RAGOps

This leads to the main conclusion of the study.

RAGOps is not simply monitoring whether the application is up.

It is the discipline of continuously asking:

Is the system still retrieving the right information for the questions our users are asking?

A production RAG pipeline should therefore have a repeatable evaluation loop:

                 ┌─────────────────┐
                 │  Golden Dataset  │
                 └────────┬────────┘
                          ↓
                 ┌─────────────────┐
                 │ Retrieval Eval  │
                 │ Recall /        │
                 │ Precision / K   │
                 └────────┬────────┘
                          ↓
                 ┌─────────────────┐
                 │ Generation Eval │
                 │ Faithfulness /  │
                 │ Answer Quality  │
                 └────────┬────────┘
                          ↓
                 ┌─────────────────┐
                 │  Deploy / Tune  │
                 └────────┬────────┘
                          ↓
                 ┌─────────────────┐
                 │ Production Data │
                 └────────┬────────┘
                          │
                          └──────→ Update Golden Set

The benchmark becomes part of the product.

The evaluation pipeline becomes part of the deployment process.

And accuracy becomes something you continuously manage rather than something you demonstrate once.

The Bigger Lesson

A RAG PoC answers:

"Can we make this work?"

Production requires answering a much harder set of questions:

"How often does it work?"
"When does it fail?"
"Can we detect the failure?"
"Can we reproduce it?"
"Can we measure whether a change actually improved it?"
"What happens when the data and user behaviour change?"

That is the gap between a RAG demo and a production RAG system.

My study started with a simple question:

How good is the retrieval?

It ended with a broader conclusion:

The hard part of production RAG is not getting an LLM to answer questions from documents. The hard part is building an engineering system that can continuously prove that the answers are grounded in the right information.

That is the problem RAGOps is ultimately trying to solve.
